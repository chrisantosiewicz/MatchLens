## Two distinct questions

1. Does MatchLens improve comprehension relative to an equally informative statistics/event-log display?
2. Does Foundry improve complete ranked next-investigation suggestions relative to a strong relevance-aware deterministic baseline?

A positive product result cannot be attributed to Foundry without the second comparison. Neither evaluation has new results. Existing operational executions retain their original scope and failures.

## Capability audit at commit802f154

The guide currently offers attributed concepts, passing/defending/involvement questions, eligible event sequences, defensive/circulation counts, evidence limits and comparable player/team box-entry windows. It uses viewer interest branches and excludes explored stable action IDs. It returns at most three actions.

The current local guide baseline sorts largely by action kind and viewing depth; it is not the proposed question-relevance baseline. Historical guide recordings cannot establish superiority over a baseline that did not exist when those calls ran.

## Freeze gate before any new model outputs

This is a protocol design, **not a completed preregistered executable evaluation**. Before execution, commit and hash all of the following together:

- Exact evaluated source, provider/model configuration, runtime limits and baseline implementation.
- Exact questions, synthetic seeds, player IDs, selected clocks, coverage, revisions, explored histories and primary answers already shown.
- Complete eligible action catalogs, maximum selections, presentation and source snapshots shared by both systems.
- Baseline relevance rules and deterministic tie-breaks, established without inspecting the new model outputs.
- Case-selection policy, ordinary/low-advantage cases, scoring rubric, exclusions and analysis script.

Prepare12–18 guide cases across currently supported capabilities. Select ordinary as well as potentially helpful situations; do not replace cases after seeing model outputs. Catalog capability checks precede outcome execution and are logged. If a discovered result prompts a fix, retain the result as development evidence and evaluate the revision with fresh cases. Do not relabel previously inspected seeds/outputs as held out.

## Equal comparison and outcome accounting

Both systems receive the same explicit question, catalog, clock, coverage, revisions, explored actions and existing answer. Both return up to three actions with identical server-authored presentation. The baseline must rank question relevance, information beyond the existing answer, availability/coverage and explored history, with a frozen stable tie-break; its exact executable scoring must be included in the freeze.

Report all intended cases and separately identify: model exercised; deterministic clarification or unsupported-request boundary; model abstention; contract rejection; timeout; other service failure; and fallback. Where instrumentation cannot distinguish outcomes, mark unknown rather than infer the cause. Deterministic boundary success is system evidence, not model-judgment credit. Token counts are usage; money is cost only when a price basis is recorded.

## Independent guide review

Use two knowledgeable reviewers uninvolved in development. Give source facts, the answer already shown and all available actions. Conceal system labels, randomize ordered-list presentation, and collect independent judgments before discussion. This is presentation-label concealment, not a claim of secure double blinding.

Score complete lists for relevance, information added beyond the answer, first-action/ranking usefulness, evidence discipline, and whether actions actually open the promised evidence at the correct clock. Keep original per-reviewer ratings and concrete reasons. Report Foundry preferred / baseline preferred / tie / neither acceptable, disagreements, later resolution and serious failures separately.

Unsupported implications include inferring pressure, defensive reactions, intended targets, space creation, continuous trajectories or causal substitution effects without suitable evidence; treating a recovery count as defensive quality; and treating a recorded sequence as an assist or sole cause. Sparse snapshots permit only their explicitly supported occupancy/endpoint statements. A fluent but unsupported implication does not win on usefulness.

## Viewer pilot

Target6–8 independent viewers with varied football familiarity. Primary outcome: comprehension accuracy. Secondary outcomes: completion time, confidence and confident errors. Use the same brief neutral orientation and ensure the statistics/event-log condition contains the facts required to answer correctly.

Each participant sees both formats with counterbalanced matched variants, without seeing the same underlying situation twice. Check the existing study's variant construction against that stronger condition before reuse; do not assume different seed/wording prevents memory transfer. Avoid leading questions and instructions revealing the preferred interpretation.

Report results per participant and descriptively overall. Participants, not task counts, are the independent people. Exclude development involvement and previously exposed/unknown-exposure sessions from first-use results using declared rules. Record interruptions and handle timing separately from accuracy. Recorded selections test comprehension with recorded outputs, not live responsiveness. Small convenience samples cannot establish broad effectiveness, demand or reliability.
